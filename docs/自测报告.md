## 一、本轮要修的问题与根因

现象：DNS 查询报 `SERVFAIL` 后立刻重查同一域名，转发器有时没重新发包就再次报错；
超时轮次的迟到上游答复还会改动缓存。根因有四处，均在 `app/resolver.py`：

1. **计时锚点不统一、UDP 端点建立耗时在时限之外。**
   旧实现里 `UdpUpstream.exchange` 自己 `wait_for(timeout=1s)`，
   而 `create_datagram_endpoint`（建立 UDP 端点）发生在计时开始之前；
   等待方又按航班起点另算一套截止时间，两条超时路径可能不一致。
2. **迟答污染缓存。** 旧 `_fetch` 只要拿到回包就 `cache.put` / `cache.delete`，
   不判断该航班是否已到硬截止；端点建立越慢，越容易出现“实际已超 1s 才到的回包”写缓存/清缓存。
3. **死航班阻塞立即重查。** 到点后航班任务可能还在后台收尾，
   新查询仍复用 `_inflight` 里这条未 `done()` 的航班，于是不再发包、直接再报错。
4. **等待中旧址失效未重新判定。** 旧址只在查询入口快照一次，
   等待回源期间若越过 30s 宽限，仍会被错误回送。

## 二、实现内容（改了什么）

### 1. 统一截止时间，UDP 端点建立计入 1s（`app/resolver.py`）

- 每个航班 `_Flight` 在建航班时记录 `started_at` 与 `hard_deadline = started_at + total_timeout`，
  所有等待方与回源任务共用这一个截止时间。
- `UdpUpstream.exchange` 在**进入方法时**先按预算算出绝对 `deadline`，
  `create_datagram_endpoint` 之后只取 `remaining = deadline - loop.time()` 等待回包；
  `remaining <= 0` 立即抛 `TimeoutError`。端点建立耗时因此被计入 1s 总时限。
- `_fetch` 传给上游的 `timeout` 也是 `hard_deadline - started`（剩余预算），
  而非重新给满 1s。

### 2. 到点结束本轮，同名新查询立即重新回源

- 等待方在 `now >= hard_deadline` 时把航班标记 `expired=True` 并结束本轮
  （回 `SERVFAIL`，或在仍可用时回 TTL0 旧址）。
- `_get_or_start_flight` 遇到 `expired` 或已 `done()` 的航班一律新建航班并重新发包，
  即使旧任务还在后台收尾。
- 旧航班的收尾回调只在“登记位仍属于自己”时移除登记，绝不替换/干扰新一轮。

### 3. 超时轮次的迟答不碰缓存

- `_fetch` 收到任何回包后先用 `_response_is_on_time`（未 `expired` 且当前时间
  `< hard_deadline`）判定；超时轮次的迟到 NOERROR/NXDOMAIN/其它 rcode 一律记日志后丢弃，
  返回 `servfail("late response after round timeout")`，**不 `put`、不 `delete`**。
- 上游自身 `wait_for` 超时时同样把航班标 `expired`。

### 4. 等待中旧址失效则继续等原回源

- 取消入口一次性快照，改为在每个决策点调用 `_stale_resolution(key)` 重新读缓存
  （底层 `AddressCache.stale_addresses` 实时按 30s 宽限判定）。
- 100ms 阈值到达时若旧址已越过宽限或已被 NXDOMAIN 清除，则不回旧址，
  继续等待**同一个**回源任务，直到硬截止回 `SERVFAIL`，期间不另发回源包。

### 5. 配套交付物

- `docker-compose.yml` 新增 `dns-forwarder-fast` 服务（400ms 总限时、grace=1s，
  宿主机 `127.0.0.1:5355`），专门演示“等待中旧址失效”。
- `scripts/demo.py` 新增第 9 段（SERVFAIL 后立即重查→重新回源）与
  第 10 段（等待回源期间旧址越过宽限→等满总限时 SERVFAIL）。
- `scripts/run_demo_local.py` 本地起栈时同步启动第三个短宽限转发进程（端口 15355）。
- `scripts/examples.sh` 增加重查与短宽限实例的手工命令。
- 测试：`tests/test_resolver.py` 新增 7 个针对性用例；新增
  `tests/test_resolver_sockets.py`（7 个真实 UDP socket 集成用例）；
  `tests/selftest_e2e.py` 新增 T11/T12 共 8 条端到端断言。

## 五、未完成项 / 已知限制（如实说明）

1. **本沙箱无法真正 `docker compose up --build`**：无 docker CLI/daemon、无 root。
   已用等价本机进程（1 个 FastAPI 上游 + 2 个转发器，演示时再加第 3 个短宽限转发器）
   完成全部运行验证；compose 文件经 YAML 解析与人工核对，首次真机 build/up 仍需在有
   Docker 的机器上确认镜像拉取与端口映射（53/5354/5355、8000）。
2. 沙箱禁止向子进程 `kill(2)`，沿用既有 stdin-EOF 看门狗（`app/runtime.py`，
   仅 `EXIT_ON_STDIN_EOF=1` 时启用，Compose/Docker 不设置该变量）；已核对测试结束后
   无残留 `app.upstream`/`app.forwarder` 进程。
3. 环境无 `dig`，README/examples 中的 dig 输出为期望样式；线路兼容性用 dnspython
   （含 EDNS OPT）与仓库自带 `scripts/dns_client.py` 实测。
4. 协议范围未变：仅 UDP、仅 A/IN，其它 qtype/class 回 `REFUSED`；
   未实现 TCP/53、DNSSEC、AAAA 转发与完整 CNAME 链。
5. NXDOMAIN 立即清旧址且不做负缓存；NODATA 透传空应答、不清旧址、不缓存。
6. 迟答判定基于转发器单调时钟与航班截止时间；若上游对同一查询在截止前后各发一个重复
   回包，截止后的回包仅被记录丢弃，截止前的有效回包已正常处理，缓存不受影响。
7. 单进程 asyncio，面向演示/小规模内网；未做源 IP ACL、限速、TCP 兜底、多上游故障切换、
   指标导出等生产加固。
